# 项目文档规范

文档要让第一次接触项目的人理解用途、完成安装并找到操作方法。更新功能时修改现有说明，不在页面开头不断追加开发汇报。

## 内容分工

| 文档 | 负责回答 | 不放什么 |
| --- | --- | --- |
| README、Wiki Home | 这是什么、能做什么、从哪里开始 | CI 记录、测试数量、本机环境和历史流水 |
| Quick-start | 如何完成第一次成功操作 | 全部参数、实现历史 |
| Installation、Updates | 怎么安装、确认连接和升级 | 相互冲突的旧版本要求 |
| 功能页 | 用途、适用目标、步骤、结果、限制 | 与本功能无关的改动和测试日志 |
| Versions | 正式下载、候选状态、兼容和待验边界 | 操作教程的重复副本 |
| Troubleshooting | 根据症状怎么检查、恢复或反馈 | 未定位故障的保证性结论 |
| 技术资料、docs、RELEASES、TODO | 设计原因、完整测量、变更、证据与开发状态 | 冒充当前用户操作指南 |

Wiki 侧栏按开始使用、日常操作、帮助与资料分组。完整页面放在 Reference 索引，不能把每份开发记录都堆进一级导航。

## 功能页写法

先写一句用途，然后按需要提供“开始前 → 操作步骤 → 结果／撤销 → 限制 → 相关页面”。简单功能可以更短，不为了模板堆空标题。

- 每一步使用实际按钮名，说明用户需要做什么以及会看到什么。
- 介绍缩写：Caps 指 CapsLock；UXP 是安装在 PS 内的执行插件。普通教程不使用 epoch、receipt、fixture 等实现词。
- 用具体例子说明容易混淆的行为，例如三个图层各转一个对象，和合成一个对象。
- 参数映射和选择比较用表格，操作顺序用编号；长段落拆成独立问题。
- 同一个概念只保留一个完整解释，其他页面链接过去。不得把一段更新说明复制到首页、安装、搜索、拆分等多个页面。

## 版本与证据

默认使用说明对应已公开的正式版本。当前正式版和开发候选集中维护在 Versions；其他页面引用它，只在确有兼容差异时写最低版本或特定范围。

主程序、内置插件、磁盘安装与 PS 实际加载版本必须区分。安装步骤不能要求过期的固定插件版本，应确认实际加载与已安装版本一致。源码或本机候选有功能，不代表下载包已经提供入口。

每个功能保留会影响用户决定的限制。自动回归、构建、切换运行入口、PS 接口、实屏和实体输入分别标注；不把未验收写成已完成。完整速度数据及失败／退化样本放技术资料，保留原测量口径，不因整理而删减或改写。

普通使用页不放单测数量、散列、临时文件路径、本机前台应用、失败夹具或按日期追加的旧“当前状态”。旧记录通过技术专题、Archive 或修订历史查阅。

## 发布前检查

1. 走读“首页 → 安装 → 第一次操作”，确认陌生读者不需要开发背景。
2. 对照正式包、界面与源码检查入口、按钮、默认键和兼容范围；没有现有 UI 的后端能力不能宣传成可操作功能。
3. 核对菜单点击与直接按键的差别，以及输入、焦点、忙碌、取消和撤销说明。
4. 检查所有内部链接、图片、代码块和导航；保留既有页面地址，必要时改为有用的指引页。
5. 保留历史证据，先保存修订，再精简当前教程。图片标明实际截图、渲染示例及版本，不用预览证明实屏通过。
6. 推送 Wiki 后核对远端修订和主要页面内容。普通文档整理不改变程序版本，也不代表新增功能已实测。
